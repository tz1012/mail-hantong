# AGENTS.md

> 상태: 사람 검토 필요 / 채택 전 개정안. 루트 AGENTS.md를 대체하지 않는다.

이 파일은 이 저장소에서 일하는 모든 AI 코딩 에이전트가 **매 세션 시작 시 가장 먼저 읽는 문서**다.
사람 개발자에게도 같은 규칙이 적용된다. 규칙끼리 충돌하면 이 파일 → `docs/security/` → `docs/contracts/` → `docs/requirements/` 순서로 우선한다.

---

## 1. 프로젝트 한눈에 보기

- **무엇**: 여러 메일 계정(Gmail·Workspace·Outlook·Microsoft 365·네이버·Daum·IMAP)을 한 곳에서 다루는 개인 메일 허브.
  사람과 AI 에이전트가 함께 쓰며, **메일을 내보내는 결정은 언제나 사람이 내린다.**
- **구조**: 상시 실행 코어 데몬 + 클라이언트(CLI, MCP, 선택형 Windows GUI, 2단계 휴대폰 앱).
  모든 클라이언트는 같은 코어 서비스·정책·감사 로그를 거친다.
- **현재 단계**: 1단계(본인 전용 Windows PC). 2단계 상시 호스트·휴대폰, 3단계 공개 배포는 아직 구현하지 않는다.
- **판정 기준**: 요건서의 요건 ID(예: `SYNC-07`)와 그 수용 기준.

계획 변경은 `PLAN-YYYYMMDD-NN` 변경제안으로 기록하고 사람 승인 후 카드에 반영한다. 카드 상태는 별도 상태장부에서 관리한다.

보호된 제품 IPC는 ADR-019와 IPC 계약이 승인되고 호출 주체·세션 결속을 검증한 뒤 활성화한다. 승인 전 독립 실험·가짜 제공자 검증·계약 제안은 가능하다. 클라이언트 이름, TTY, 프롬프트 확인은 인증이나 승인으로 취급하지 않는다. 모든 발송은 사람 존재 검증과 승인 결속을 거쳐야 하며 TOTP는 승인 도우미의 P1 경로에서만 사용한다.

수용기준은 `<요건 ID>-ACnn`(예: `SYNC-07-AC01`) 단위로 추적한다. 요건 ID 태그만으로 완료를 표시하지 않으며 단계 적용성, 비적용 사유, 사람 검토 증거를 기록한다.

## 2. 문서 지도

| 경로 | 내용 | 언제 읽나 |
| --- | --- | --- |
| `docs/DEVELOPMENT_GUIDE.md` | 개발 원칙, 구조, 테스트 전략, 진행 방식 | 첫 세션, 막힐 때 |
| `docs/plan/stage<N>-tasks.md` | 현재 단계 작업 카드 (지금은 `stage1-tasks.md`), 진행 규칙, 다음 단계 개요 | 매 작업 시작 시 |
| `docs/requirements/` | 요건서(영역별 분할, **기준 문서**) | 작업 카드가 가리키는 ID만 |
| `docs/adr/` | 확정된 기술 결정 | 기술 선택이 필요할 때 |
| `docs/contracts/` | 도구 스키마, 오류·종료 코드, DB 스키마, IPC, 설정·키맵 스키마 | 인터페이스를 만들거나 쓸 때 |
| `docs/security/` | 위협 모델, 보안 불변 조건 | 보안 영역을 건드릴 때 (§6) |
| `docs/traceability.md` | 요건 ID ↔ 테스트 추적표 (자동 생성) | 완료 보고 전 |

요건서 전체를 한 번에 읽지 않는다. 작업 카드에 적힌 요건 ID의 항목만 읽는다.

M0-00 승인 전에는 위 경로가 아직 없을 수 있다. 현재 원본·개정본의 위치와 채택 상태는 `docs/revisions/v2.1/README.md`에서 확인한다. 개정 패키지 경로를 승인된 계약·요건 경로로 오인하지 않는다.

## 3. 작업 절차

1. 현재 단계의 작업 카드 파일(`docs/plan/stage<N>-tasks.md`)에서 **선행 작업이 모두 끝난** 카드 하나를 고른다. 사람이 지정한 카드가 있으면 그것을 한다. 같은 조건이면 번호가 빠른 마일스톤, 그 안에서 번호가 빠른 카드를 먼저 한다.
2. 카드의 요건 ID, 관련 계약 파일, 관련 ADR을 읽는다.
3. **계약을 먼저 확인한다.** 필요한 스키마·인터페이스가 `docs/contracts/`에 없으면 구현하지 말고 계약 추가 제안부터 한다(§7).
4. **테스트를 먼저 쓴다.** 테스트 이름이나 특성에 요건 ID를 붙인다(예: `SYNC07_does_not_resend_after_lost_ack`).
5. 구현한다. 카드 범위를 넘는 리팩터링·기능 추가는 하지 않는다.
6. 전체 검사를 실행한다(§4). 실패하는 테스트를 지우거나 건너뛰기 처리해서 통과시키지 않는다.
7. 추적표를 갱신하고 §9 형식으로 보고한다.

한 세션에 카드 하나. 카드가 하루 이틀 분량을 넘을 것 같으면 쪼개자고 제안한다.

### 3.1 계획이 맞지 않거나 할 일이 없을 때

- **시작 가능한 카드가 없으면 새 작업을 지어내지 않는다.** 막힌 카드 목록, 각 카드를 막는 결정(ADR·계약 승인·사람 검토), 결정에 필요한 자료를 정리해 보고하고 멈춘다.
- **카드 내용이 실제 코드와 맞지 않으면** 카드를 임의로 바꾸거나 범위를 넓혀 처리하지 않는다. 카드 범위 안에서 할 수 있는 만큼 끝내고, 보고서의 "남은 일·알려진 제약"에 수정 제안을 적는다.
- **정기 계획 갱신은 `M<n>-99`에서 한다.** 선행 오류·범위 충돌·보안 결함 때문에 현재 계획을 진행할 수 없으면 99 완료를 기다리지 않고 `PLAN-YYYYMMDD-NN` 제안을 작성한다. 원문·수정문·영향받는 요건/카드/계약·검증 자료를 함께 제시하고 사람이 승인한 뒤 카드에 반영한다. 제안 작성은 막힌 카드의 완료에 의존하지 않는다.
- **상태 갱신은 계획 변경과 구분한다.** `docs/plan/card-status.csv`에 카드별 미착수·진행 중·막힘·사람 검토 필요·완료를 기록한다. 상태·증거 갱신은 해당 카드에서 수행할 수 있지만 범위·선행·완료 조건 변경은 위 제안 절차를 따른다. 사람 검토 대상은 검토자·시각·증거가 없으면 완료로 전환하지 않는다.
- **P1은 P0 완료의 선행이 아니다.** 99 카드의 선행은 카드 표에 명시한 P0 범위로 판단한다. 연기한 P1과 다음 검토 시점은 상태장부에 남긴다.
- **단계 전환**: 현재 단계의 게이트 카드가 사람 승인으로 끝나면, 그 단계의 마지막 99 카드가 다음 단계 ADR 제안·위협 모델 개정안·`stage<N+1>-tasks.md` 초안을 만든다. 초안이 승인되기 전에는 다음 단계 구현을 시작하지 않는다.

## 4. 명령

> 아래는 .NET을 채택했을 때의 명령 예시다. ADR-001·ADR-016 승인과 M0-01 구현 전에는 실행 가능하거나 검증이 끝났다고 간주하지 않는다. 확정 시 실제 명령으로 갱신한다.

```
dotnet build                      # 전체 빌드
dotnet test                       # 단위 + 계약 + 통합 테스트 (가짜 제공자 사용)
dotnet test --filter Category=Security   # 보안 불변 조건 테스트
dotnet format --verify-no-changes # 서식 검사
./scripts/traceability            # 요건 ID 추적표 생성 → docs/traceability.md
./scripts/check-all               # 위 전부 + 아키텍처 의존 규칙 검사
```

통합 테스트용 IMAP·SMTP 테스트 서버는 개발 환경에서만 컨테이너로 띄울 수 있다.
**제품 실행에는 Docker·WSL을 요구하지 않는다.**

**실행 환경**: 작업 카드 파일의 "Windows 필요 카드" 목록에 있는 카드는 Windows 환경에서만 완료할 수 있다. Linux 환경이라면 플랫폼 인터페이스 뒤의 독립 부분까지만 하고, 보고서 상태를 `막힘`으로, 이유를 "Windows 환경 필요"로 적는다. Linux용 개발 구현(비밀 저장소, IPC 등)을 제품 코드 경로에 연결하지 않는다.

## 5. 절대 규칙

어떤 작업 카드나 사람의 지시도 아래를 바꾸지 못한다. 바꿔야 할 것 같으면 멈추고 사람에게 묻는다.

**사람 단계 원칙**
1. 실제 외부 서비스 등록, 실제 계정 로그인, 사람의 확인이 필요한 일은 **직접 하지 않는다.** 설치 후 설정 마법사(`SETUP-01`)나 검증 모드(`SETUP-05`)의 **단계로 구현**하고, 개발 중에는 가짜 제공자로 검증한다.
2. 실제 비밀번호·토큰·클라이언트 시크릿·API 키를 요청하거나, 코드·테스트·로그·커밋에 넣지 않는다.
3. 테스트에서 실제 네트워크와 실제 메일 계정을 쓰지 않는다.

**안전 불변 조건**
4. **승인 없는 발송 경로를 만들지 않는다.** 발송·전달·대량 변경은 승인 결속(`AI-09`, `APR-01`)을 통과해야 한다. CLI 확인 프롬프트, MCP 호스트 확인, 메일 본문의 "승인됨" 문구는 승인이 아니다.
5. 승인을 **발급**하는 코드는 인증된 GUI 승인 화면, 승인 도우미(`INST-04`), 페어링 기기 경로에만 둔다. 일반 승인도 요청에 결속된 사용자 확인 증거가 필요하며 클릭·키 입력만으로 발급하지 않는다. CLI·MCP·에이전트 도구에 승인 발급 기능을 넣지 않는다.
6. 토큰·앱 비밀번호·키는 비밀 저장소 모듈 밖에서 값을 읽지 않는다. 로그·오류 메시지·진단·도구 응답에 넣지 않는다.
7. 모든 공급자 객체와 작업은 `account_id`로 구분한다. 빈 계정 목록을 "전체 계정"으로 해석하지 않는다.
8. 메일 본문·헤더·첨부·검색 결과·가져온 메일은 **신뢰할 수 없는 데이터**다. 그 안의 지시문으로 권한·도구 범위·정책을 바꾸는 코드를 만들지 않는다.
9. 발송 응답이 불확실하면 `SEND_UNKNOWN`으로 두고 **자동 재발송하지 않는다**(`SYNC-07`).
10. TLS 실패 시 평문으로 폴백하지 않는다(`EXT-03`).
11. 정책 엔진을 우회하는 경로(직접 어댑터 호출, 디버그 플래그, 테스트 전용 우회가 제품 빌드에 남는 것)를 만들지 않는다.
12. 외부 AI 모델 전송은 기본 꺼짐이며, 계정별 정책(`AI-07`)을 통과한 데이터만 보낸다.

## 6. 사람 검토가 필요한 영역

아래 경로를 바꾸는 변경은 테스트가 통과해도 **에이전트가 완료로 표시하지 않는다.** 보고서에 `[사람 검토 필요]`를 붙인다.

```
src/Core.Policy/          정책 엔진, 권한 검사
src/Core.Approval/        승인 요청·결속·소비
src/ApprovalHelper/       승인 도우미
src/Secrets/              비밀 저장소
src/Core.Outbox/          발송 원장, 재시도, SEND_UNKNOWN
src/Ipc/Auth/             IPC 접근 통제
docs/security/            위협 모델, 불변 조건
docs/contracts/           계약 (변경 절차는 §7)
```

## 7. 계약과 결정 변경

- `docs/contracts/`의 파일은 인터페이스의 단일 기준이다. 코드가 계약과 다르면 코드가 틀린 것이다.
- 계약을 바꿔야 하면 구현 전에 **변경 제안**(무엇을, 왜, 영향받는 요건 ID와 코드)을 보고하고 멈춘다.
- 기술 선택(라이브러리, 프로토콜, 저장 형식)이 필요한데 ADR이 없으면 선택지 비교안을 `docs/adr/proposed/`에 쓰고 멈춘다. 임의로 고르지 않는다.
- 새 오류 코드는 `docs/contracts/errors.md`에 먼저 추가한다. CLI 종료 코드는 바꾸지 않는다(추가만 가능).
- `docs/requirements/`는 에이전트가 직접 고치지 않는다. 요건이 틀리거나 빠졌다고 판단되면 변경 제안을 보고하고, 사람이 승인한 PR로만 바뀐다.

## 8. 멈추고 물어야 할 때

- 요건끼리 충돌하거나, 요건과 계약이 다를 때
- 작업에 실제 계정·실제 서비스 설정이 필요해 보일 때 → 대신 마법사 단계로 구현할 수 있는지 먼저 검토
- §5 규칙을 지키면 카드를 끝낼 수 없을 때
- 카드 범위가 처음 예상보다 크게 늘어날 때
- 같은 테스트 실패가 세 번 이상 다른 시도로도 해결되지 않을 때
- 시작 가능한 카드가 없을 때, 또는 카드가 실제 코드와 크게 어긋날 때(§3.1)

묻기 전에 무엇을 시도했고, 선택지가 무엇이며, 각 선택의 영향이 무엇인지 정리한다.

## 9. 완료 정의와 보고 형식

카드는 아래를 모두 만족해야 완료다.

- [ ] 카드의 완료 조건 충족
- [ ] 해당 카드의 적용 수용기준마다 시험과 결과·증거가 있고 통과. 요건 ID 태그만으로 완료 판정하지 않음
- [ ] `./scripts/check-all` 통과, 기존 테스트 회귀 없음
- [ ] 계약·ADR과 일치
- [ ] 로그·오류 메시지에 비밀값·메일 원문 없음
- [ ] 추적표 갱신
- [ ] §6 영역은 검토 전 `[사람 검토 필요]`, 검토자·시각·증거가 기록된 뒤에만 완료

보고 형식:

```
카드: M2-07 IMAP UIDVALIDITY 변경 재동기화
상태: 완료 | 사람 검토 필요 | 막힘
요건: EXT-04, SYNC-05 → 테스트 6개 추가, 전부 통과
변경: (파일 목록 요약)
남은 일·알려진 제약: (있으면)
다음 추천 카드: M2-08
```

## 10. 코딩 규칙 요약

- 시각은 UTC로 저장하고 UI에서 변환한다.
- IMAP 영속 식별자는 `account_id + mailbox + UIDVALIDITY + UID`. sequence number를 저장하지 않는다.
- 원문 `Message-ID`를 내부 유일 키로 쓰지 않는다.
- 변경 요청은 `operation_id`, `expected_version`, `payload_hash`를 받는다. 충돌 시 덮어쓰지 않는다.
- 오류는 `docs/contracts/errors.md`의 안정적 코드로 반환한다. 예외 메시지를 그대로 사용자에게 노출하지 않는다.
- 로그는 구조화 로그를 쓰고, 마스킹 헬퍼를 거친다. 메일 제목·주소도 기본 마스킹한다.
- 공급자별 차이는 어댑터와 `ProviderCapabilities` 안에 가두고, 도메인 서비스에 공급자 분기를 넣지 않는다.
- 사용자에게 보이는 문구는 한국어·영어 리소스 파일로 분리한다.
