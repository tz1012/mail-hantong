# Google multi-account desktop login and Gmail read

Implementation contract, ACC-01/02/03/04/05/06, SYNC-02, INST-03. **Human security review required.** The user's current instruction authorizes local implementation, not actual Google project registration, account login or provider calls in development.

- Desktop authorization-code OAuth uses the system browser, fresh random state and PKCE S256, a five-minute IPv4 `127.0.0.1` ephemeral-port listener, exact callback path/Host/state and one-time consumption. No embedded webview, passwords, caller-supplied callbacks, token arguments or plaintext token getters. Reject duplicate query fields, stale state and callback replay. Browser errors return stable codes without descriptions/code/verifier/token reflection.
- Request exactly `openid email https://www.googleapis.com/auth/gmail.readonly`, `access_type=offline`, `prompt=select_account`; do not request incremental scope accumulation. A deliberate reauthorization may request consent again to obtain a missing refresh token. Desktop client ID is public configuration; no invented/default ID or publisher secret is shipped. Accept an explicit valid Desktop client ID on first setup and remember it after verified activation. Google project/API/consent/verification setup is a human wizard prerequisite. For Desktop clients requiring client_secret, a separate core-owned protected input review precedes browser launch. It binds the exact public client ID, fixed Google token endpoint, request and capture nonce; Windows verification is required before transmission. The opaque value never becomes a CLI argument, ordinary IPC field, config value or log. It is sent only by Secrets to the fixed Google TLS token endpoint for code exchange and refresh. Final verified account publication stores it with the account/subject/client/version-bound DPAPI bundle (format 4); legacy format 3 without a secret remains readable. Rotation preserves the secret and binding. Cancellation or failed login discards the pending value. After a successful connection, later additions may reuse only the same client ID’s opaque credential from a verified protected bundle; account tokens remain isolated. See [Google onboarding](google-onboarding.md). Legacy or first-use capture still requires native verification; background refresh uses only its own verified account bundle.
- Only Secrets exchanges codes at `https://oauth2.googleapis.com/token`, reads verified identity from `https://openidconnect.googleapis.com/v1/userinfo`, refreshes tokens and uses Gmail at `https://gmail.googleapis.com/gmail/v1/users/me/`. Fixed HTTPS hosts, OS certificate/hostname validation, no redirects or plaintext fallback, bounded bytes/deadlines and no raw provider errors. Validate actual granted Gmail scope and stable UserInfo sub/email_verified. Email is display metadata, never account identity.
- `GoogleAccountBinding { account_id, subject, client_id, credential_version }` binds every token/cache/job to the stable Google subject and client configuration. Account ID is `google_` plus lowercase SHA256(subject UTF-8). Tokens are held and wiped inside Secrets and stored in new case-safe, generation-specific DPAPI slots; legacy OAuth/mail slots are not reused. Refresh is serialized per account. Missing/invalid refresh, revoked grant or changed subject fails that account without retry loops or cross-account fallback. Existing cached mail remains local.
- Browser completion yields an opaque pending credential. Native Core-owned review displays exact account/email/client/read scope and requires existing human verification before credential publication and Store activation. This is account setup, not mail-send approval. Reconnecting a subject reuses its account ID and performs version CAS; different subjects remain separate. No client profile gains new account scopes automatically: explicit registration/refresh review remains required.
- Gmail is read-only even if a provider returns broader scopes. No Gmail mutation/send API exists. List labels, bounded newest-message pages and message details through Gmail REST; preserve Gmail message/label IDs, never fabricate IMAP UIDVALIDITY/UID. Inline MIME text is sanitized and bounded to64KiB; attachments/remote content are not opened.
- Authenticated Gmail operations use the existing common scope/policy/rate/audit coordinator and existing tool IDs with explicit `mode` variants: `mail.folders.list` gmail_labels; `mail.messages.search` gmail_messages; `mail.messages.get` gmail_body; `mail.sync.page` gmail_page; sync status gmail_status. Every request carries explicit account_id. Sync includes operation/idempotency/expected_version and an account-scoped provider page token. One account's failure must not block the other connected accounts. Read calls use encrypted local cache; network synchronization is explicit and audited.
- Store v19 adds Google connection/configuration, labels, cached messages, per-account sync state and durable sync request ledgers. Admission and completion retain registration/epoch/account/version binding and atomic audit completion; restart records interrupted jobs without automatic network replay. No migrations/startup path creates accounts, OAuth grants or AI consent.
- CLI exposes protected Google setup/status, authenticated Gmail labels/sync/status/list/read and an interactive Google-login orchestration. Existing terminal browser invokes the same CLI/Core operations. MCP can discover the same explicit Gmail request variants and remains independently registered with per-account external-AI consent.

Official evidence: [Desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app), [OIDC identity](https://developers.google.com/identity/openid-connect/reference), [Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes), [IMAP full-mail scope](https://developers.google.com/workspace/gmail/imap/xoauth2-protocol). Public restricted-scope OAuth verification and real-provider interoperability remain external release gates.

## 2026-11-02 bounded attachment re-verification

`gmail sync --message-id ID --limit 1` selects exactly one message through the same authenticated account/scope/audit/read path. It is mutually exclusive with label_id and page_token. Secrets validates the requested ID before building a fixed users/me detail URL; both Secrets and Store reject a substituted result. Optional message_id is part of idempotency/CAS binding; omission preserves historical serialized requests and needs no migration. No send, grant or provider permission is added.

Attachment IDs have a separate 4096-byte URL-safe component bound; message IDs retain their existing bound, whole request paths remain capped at 8192 bytes, and attachment count/decoded size, account isolation and TLS checks remain unchanged. Diagnostics contain only closed stage/outcome/error enums and timing, never identifiers, credentials, filenames or message content. See the official [attachment resource](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages.attachments). Human security review remains required.

## 2026-11-02 large-body preview correction

Manual provider review found an ordinary ~96KB message was entirely unreadable
because the old renderer applied its 64KiB output limit before HTML decoding.
Keep the 2MiB Gmail detail response bound, MIME depth/part count bounds, attachment
exclusion and text-only sanitization. Decode each selected text part within the
existing 1MiB MIME input budget (reserving bounded Content-Type header space).
Render safe text first, then retain at most 64KiB on a UTF-8 character boundary.
Multipart aggregation observes that same total retained-text bound. Report
truncated=true when visible text was omitted; never return QUOTA_EXCEEDED merely
because a valid rendered body exceeds the output limit. Metadata-only responses,
input over the separate parsing budget, invalid encodings and unsupported bodies
remain explicit errors. No script, HTML, remote image or attachment is executed
or loaded. The CLI's existing truncation notice remains mandatory.
