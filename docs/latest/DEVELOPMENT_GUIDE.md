## 1. 개발 원칙

1. **사람 단계는 제품 기능으로 만든다.**
   외부 서비스 등록(OAuth 클라이언트, Pub/Sub), 실제 로그인, 앱 비밀번호 입력, Windows Hello 등록, 실제 계정 확인은 개발 중에 미리 하지 않는다. 설치 후 설정 마법사(`SETUP-01~03`)와 검증 모드(`SETUP-05`)의 단계로 구현한다. 개발은 가짜 제공자로 검증하고, 실제 연결은 설치한 사람이 마법사를 따라 끝낸다.
2. **계약 먼저, 테스트 먼저, 구현은 마지막.**
   인터페이스는 `docs/contracts/`에 먼저 존재해야 하고, 요건 ID가 붙은 테스트가 구현보다 먼저 존재해야 한다.
3. **하나의 코어, 여러 클라이언트.**
   CLI·MCP·GUI·승인 도우미는 IPC로 코어를 호출하는 얇은 계층이다. 클라이언트에 비즈니스 로직, 공급자 호출, DB 접근을 넣지 않는다.
4. **안전 불변 조건은 테스트로 고정한다.**
   "무승인 발송 없음", "계정 간 유출 없음", "자동 중복 발송 없음", "토큰 노출 없음"은 문서가 아니라 실행 가능한 보안 테스트 묶음으로 존재해야 한다. Rust 시험 구조에서 실제 실행 명령과 누락 검사를 연결한다.
5. **공급자 차이는 숨기지 않고 가둔다.**
   Gmail 라벨, IMAP 폴더, Graph delta의 차이는 어댑터와 `ProviderCapabilities` 안에서 처리하고, 위로는 능력(capability)으로 드러낸다.
6. **작게 끝낸다.**
   작업 카드는 에이전트 한 세션(대략 하루 이틀)에 끝나는 크기로 유지한다. 끝나지 않는 카드는 쪼갠다.

## 4. 계약 파일

`docs/contracts/`는 코드보다 먼저 존재한다. 각 파일에는 버전이 있고, 바꿀 때는 변경 제안 → 사람 확인 → 버전 증가 순서를 따른다. 계약 산출 카드도 사람 검토 카드로 분류한다.

보호된 IPC는 인증된 호출 주체와 세션 결속을 확인하기 전 허용하지 않는다. 클라이언트 명칭, TTY 여부, 프로세스 표시만으로 인증하지 않는다. ADR-019와 IPC 계약 승인 전에는 독립 실험·가짜 검증만 수행하고 보호된 제품 IPC를 활성화하지 않는다. 미등록 호출은 버전·준비 상태·등록 요청만 허용하고 accounts.list를 포함한 계정·메일 정보는 반환하지 않는다.

모든 발송은 신뢰 채널의 사람 존재 확인과 승인 결속을 요구한다. TOTP는 P1 대체 수단이며 승인 도우미 경로에서만 처리하고 터미널 발급·입력 경로는 만들지 않는다. 코어 전용 설치에는 승인 도우미 보안 설정 화면이 필요하다.

백업 서버 업로드는 대상 계정의 capability, 날짜 보존, 외부 규칙·알림 부작용을 검증한 조합에서만 활성화한다. 검증되지 않은 조합은 CAPABILITY_UNSUPPORTED로 사전 거부하며 로컬 보관함을 기본 경로로 둔다. 비활성화가 P0 자동 면제는 아니다. 출시 지원 범위와 날짜·서버 부작용 조건은 요건서 §12.1.1과 사람 검토로 확정한다.

추적표는 요건 ID와 별도로 각 수용기준에 `<요건 ID>-ACnn`(예: `SYNC-07-AC01`) 식별자를 기록한다. 요건 ID 태그만으로 완료를 판정하지 않으며 단계 적용성, 비적용 사유, 사람 검토 증거를 함께 기록한다.

## 5. 모듈 경계와 의존 규칙

```
Clients:   Cli   Mcp   Gui   ApprovalHelper           (IPC 클라이언트만 참조)
              \    |    /      /
IPC:           Ipc.Client  ←→  Ipc.Server (+ Ipc/Auth)
                                   |
Core:      Core.Application  →  Core.Policy  →  Core.Approval
               |        |             |
           Core.Domain  Workers(Sync, Outbox, Events, Backup)
               |
Infra:     Store(DB·검색·첨부)   Secrets   Adapters.{Gmail, Graph, Imap, Smtp}
```

의존 규칙(아키텍처 테스트로 강제):

- 클라이언트 프로젝트는 `Ipc.Client`와 계약 DTO만 참조한다. `Store`, `Secrets`, `Adapters`를 참조하면 빌드 실패.
- `Adapters`는 `Core.Domain`의 인터페이스만 안다. 정책·승인을 모르며, 토큰은 호출 시 `Secrets`가 넘긴 핸들로만 받는다.
- 비밀값을 평문으로 다루는 타입은 `Secrets` 안에만 존재한다.
- 발송은 오직 `Core.Outbox`를 통해서만 어댑터의 send를 호출한다. 다른 곳에서 send 호출 시 아키텍처 테스트 실패.
- `Core.Approval`의 승인 발급 API는 인증된 승인 전용 세션과 요청에 결속된 사용자 확인 증거를 모두 검사한다. 일반 GUI 클릭만으로 승인하지 않는다. M5 통합 전 발송·승인 필요 변경 경로는 거부 상태로 유지한다.

### 6.1 개발 환경과 CI

코어는 Windows·Linux 공용이지만, 일부 기능은 Windows에서만 빌드·검증할 수 있다. 클라우드 코딩 에이전트는 대개 Linux에서 동작하므로, 카드를 실행 환경으로 나눈다.

| 환경 | 맡는 일 | 비고 |
| --- | --- | --- |
| Linux (에이전트 기본) | 도메인, 정책, 승인 로직, 어댑터, 동기화, 검색, CLI·MCP, 백업, 이벤트 | 개발용 비밀 저장소(암호화 파일)와 유닉스 소켓 IPC로 동작. 제품 빌드에는 포함되지 않음 |
| Windows (개발 PC 또는 Windows CI 러너) | DPAPI 비밀 저장소, 명명된 파이프 ACL, 승인 도우미, Windows Hello, 토스트, 콘솔 UTF-8, GUI, 설치 패키지, 자동 시작 | `stage1-tasks.md`의 "Windows 필요 카드" 목록 |

플랫폼 의존 부분은 인터페이스 뒤에 둔다(`ISecretStore`, `IIpcTransport`, `INotifier`, `IUserVerifier`, `IAutoStart`). Linux 구현은 개발·테스트용이고, 제품 빌드는 Windows 구현만 쓴다(2단계 Linux 호스트는 HOST-02에서 제품용 구현을 따로 만든다).

CI는 두 갈래로 돌린다.
- **Linux 러너**: 단위·계약·통합(테스트 메일 서버 컨테이너)·종단·보안 테스트
- **Windows 러너**: 플랫폼 구현 테스트, GUI 빌드, 설치 패키지 빌드, 콘솔 한글 시험

두 갈래가 모두 통과해야 병합한다. Windows 필요 카드를 Linux 환경의 에이전트가 맡게 되면, 플랫폼 독립 부분까지만 하고 나머지는 보고서에 "Windows 환경 필요"로 남긴다.

## 10. 작업 진행 방식

진행 상황은 [PROGRESS.md](PROGRESS.md) 한 문서에 누적한다. 작업 시작 시 현재 상태와 다음 작업을 읽고, 종료 시 변경 파일·검증 명령과 결과·미해결 결정·다음 작업을 갱신한다. 카드 상태장부도 함께 맞추되 요건·계약·기술 결정의 승인 기록을 대신하지 않는다. GitHub 공개와 명령어 설치·개발 환경 목표는 [DISTRIBUTION.md](DISTRIBUTION.md)를 참고한다.

**작업 카드 형식** (`docs/plan/stage1-tasks.md`)

| 필드 | 설명 |
| --- | --- |
| ID | `M<마일스톤>-<번호>` |
| 제목 | 한 줄 |
| 요건 | 요건 ID 목록 |
| 선행 | 먼저 끝나야 할 카드 |
| 산출물 | 코드·계약·테스트 |
| 완료 조건 | 통과해야 할 테스트·확인 |
| 검토 | `에이전트` 또는 `사람` (§8) |

**상태와 근거**
- `docs/plan/card-status.csv`를 카드별 상태의 기준으로 사용한다. 범위·선행 수정과 상태 갱신을 분리한다.
- 상태는 `not_started`, `in_progress`, `blocked`, `review_required`, `complete`다. `complete`는 수용기준 증거가 있고 사람 검토 대상이면 승인자·시각·근거도 있을 때만 쓴다.
- P1 카드가 P0 마일스톤·Gate 1을 막지 않는다. Gate 1은 요건서 §15.2.1의 단계별 적용 기준과 실계정 증거를 확인한다.

**브랜치·커밋**
- 브랜치: `task/M2-07-uidvalidity`
- 커밋 메시지 첫 줄에 카드 ID와 요건 ID: `M2-07 EXT-04 UIDVALIDITY 변경 시 사서함 재동기화`
- PR 설명에 AGENTS.md §9 보고 형식을 붙인다.

**병렬 작업**
- 선행 관계가 없는 카드는 별도 작업 트리에서 병렬로 진행할 수 있다.
- 같은 계약 파일을 바꾸는 카드는 병렬로 돌리지 않는다.
- 보안 영역 카드는 한 번에 하나씩 진행하고, 사람 검토가 끝난 뒤 다음으로 넘어간다.

**사람의 역할**
- ADR 확정, 계약 변경 승인, 보안 영역 검토, 마일스톤 종료 시 검증 모드 실행.
- 그 외 구현·테스트·문서 갱신은 에이전트가 맡는다.

### 롤링 계획

카드는 코드가 생기기 전에 쓴 계획이므로 진행하며 어긋난다. 그래서 모든 마일스톤은 `M<n>-99 다음 마일스톤 계획 갱신` 카드로 끝난다. 이 카드는 실제 코드·추적표를 기준으로 다음 마일스톤 카드를 고치는 수정안을 만들고, 사람이 승인하면 반영한다. 진행을 막는 선행 오류·범위 충돌은 `PLAN-YYYYMMDD-NN`으로 즉시 수정안을 작성할 수 있고, 99 카드 완료와 무관하게 사람 승인 후 반영한다(AGENTS.md §3.1). 요건 ID와 카드의 대조는 M0-04 추적표 스크립트가 맡으며, 미커버 P0 요건은 99 카드에서 새 카드로 제안한다.

### 2단계·3단계 (개요)

세부 마일스톤 틀은 `stage1-tasks.md` 끝의 "2단계·3단계 개요"에 있다. M9-99 카드가 이를 바탕으로 2단계 ADR 제안(모바일, 헤드리스 비밀 저장소, 릴레이, 원격 인증), 위협 모델 개정안, `stage2-tasks.md` 초안을 만들고, 사람이 승인한 뒤 2단계 구현을 시작한다. 3단계도 2단계 게이트 이후 같은 방식으로 만든다.

## 12. 문서 유지 규칙

- 요건서의 기준은 저장소 `docs/requirements/`다(M0-00 이후). 요건 변경은 PR로 하고 사람이 승인한다. 에이전트는 요건 파일을 직접 고치지 않고 변경 제안만 한다.
- 요건이 바뀌면 ID를 유지하고 내용만 고친다. 삭제한 요건 ID는 재사용하지 않는다.
- 요건 변경 → 관련 작업 카드·계약·테스트를 같은 PR 또는 연이은 PR에서 고친다.
- 다른 앱의 단축키, 공급자 정책·할당량처럼 외부에 의존하는 사실은 출처와 확인 날짜를 함께 적고, 출시 전에 다시 확인한다.
- 이 지침서는 마일스톤이 끝날 때마다 다시 읽고 고친다.
