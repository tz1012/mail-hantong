# Google 인증 UI와 Windows Hello 반복 검토 (2026-11-02)

상태: 읽기 전용 검토안. 코드·보안 정책·실제 권한은 변경하지 않았다. 기존 전체 검사 1,699개 통과와 실제 양방향 첨부 검증 결과는 보존한다. **구현 전 사람 보안 검토 필요**.

## Ask Aside 확인 범위

공식 CUA 도구 문서와 Windows 창 목록을 조회했다. 현재 연결된 창은 Chrome이며 Aside 창은 목록에 없었다. 브라우저 3은 조회 가능했고 이전 브라우저 4는 `Browser is not available: 4`로 응답했다. 따라서 이 세션에서 Ask Aside 기능의 존재나 Google OAuth 화면 조작 지원은 확인하지 못했다. 반복 timeout이나 다른 경로 우회는 하지 않았다. 페이지 내부 버튼 부재만으로 브라우저 기능 자체가 없다고 결론내리지 않는다.

현재 지원되는 도구 문서에는 일반 탭 조회·DOM 읽기·일반 화면 조작은 있으나 Ask Aside 전용 기능은 명시되지 않았다. Ask Aside가 해당 설치 환경에 존재하더라도 Google 동의·보안 경고·Windows Hello를 대신할 수 있다고 추정하지 않는다. 실제 인증 화면 지원 여부를 확인하려고 새 OAuth를 만들거나 인증 URL·code/state·토큰·비밀값을 다른 에이전트에 전달하지 않았다. Google 콘솔의 Gemini Cloud Assist는 확인됐지만 이를 Ask Aside로 혼동하지 않는다.

## 현재 Hello가 반복된 이유

Google 계정별 동의 및 보호 저장, 로컬 CLI 권한 갱신, 개별 발송 승인은 서로 다른 목적이다. 로컬 `apps/mail-hantong-core/src/scope_refresh.rs`의 `google_changes_scope`는 기존 공통 발송 도구 집합 또는 변경 도구 집합을 전제로 한다. 먼저 두 계정의 공통 읽기·발송 범위를 만들고 이후 선택 계정에만 변경 grant를 추가하는 구조라 두 번의 로컬 승인으로 나뉜다. 이것은 현재 API·저장/승인 흐름의 제약이며 Windows Hello 자체가 항상 이 순서를 요구한다는 뜻은 아니다. 이미 활성화된 동일 grant의 일반 읽기는 새 Hello를 요구하는 설계가 아니다.

`docs/contracts/google-write.md`는 Google grant, 로컬 profile grant와 일회성 발송 승인을 구분한다. Google 권한을 얻었다는 사실만으로 로컬 발송 승인이 생기지 않는다.

## 권장 검토안: 계정별 권한표를 한 번 확인

하나의 네이티브 화면에 각 계정을 별도 행으로 표시하고 기존 권한·추가 권한·Google 권한 확보 여부·자동 만료 없음·철회 방법을 보여준다. 예를 들어 A는 읽기/발송, B는 읽기/발송/초안/읽음·라벨 변경만 선택한다. 모든 계정에 합집합 권한을 적용하지 않는다. 변경 없는 계정은 기존 grant를 재사용한다.

한 요청의 서명/승인 대상에는 등록 ID·epoch, 계정별 정렬된 최소 tool 집합, 기존 버전과 목표 버전, payload hash, nonce, 만료시각이 모두 포함돼야 한다. 기존 native Hello 확인 1회 후 전체 권한표를 원자적으로 활성화하거나 모두 취소한다. 저장 중 실패·프로필 교체·계정 상태 변화·만료·재시작·재생에서는 부분 권한 확장이나 자동 재승인이 없어야 한다. UI 준비 완료 후 요청을 만들며 기존 300초 보호 TTL을 늘리지 않는다.

필요 변경은 계약의 계정별 권한표, native 승인 UI, Store/IPC의 비교·활성화·복구 경로, 감사 기록 및 합성 격리 테스트다. 권한 확인 생략이나 Hello 우회가 아니다. Google 계정별 동의와 필요 시 자격증명 보호 저장 확인은 별도로 유지한다. 구현/실제 적용 전 보안 검토와 변경될 정확한 지속 권한 승인 범위를 제시해야 한다.

## 발송 확인의 두 선택지

| 선택지 | 보장·위험 | 필요한 승인 |
| --- | --- | --- |
| 메일별 확인 유지 (기본 권장) | 발신 계정·수신자·본문·첨부 snapshot이 각 일회성 승인과 결속된다. 확인 횟수는 메일 수만큼 남는다. | 현재 계약과 네이티브 메일별 확인 유지. 새 권한 확대 없음. |
| 명시적인 제한 묶음 검토 | 사용자가 펼쳐 볼 수 있는 유한한 N건의 정확한 발신 계정·수신자·본문·첨부 해시를 한 번 검토한다. 한 번의 실수로 여러 건을 승인하는 위험이 커진다. 기간 내 무제한 발송이나 나중에 내용 추가는 금지한다. | 묶음 승인이라는 보안 동작 변경에 대한 별도 구체 승인·사람 보안 검토·계약/구현/테스트가 필요하다. 이번 읽기 검토는 적용 승인이 아니다. |

제한 묶음도 각 항목에 개별 일회성 claim·감사·결과 상태를 유지하고, 어느 한 건이 불확실하면 그 건을 자동 재발송하지 않는다. 미사용 항목 취소와 만료가 가능해야 한다. 기존 두 시험 메일은 이미 완료됐으므로 이 설계 검토를 이유로 다시 보내지 않는다.
