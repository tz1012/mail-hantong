# mail-hantong UX UI 가이드

## 기준과 적용 범위

상태: Active. 제품 이름, CLI 이름, 영·한 지원과 세 가지 테마는 사용자가 정한 필수 조건이다. 구체적인 색상값과 치수는 GUI 프로토타입에서 검증한다. 갱신일은 2026년 10월 30일이다.

제품·솔루션 이름은 **mail-hantong**, CLI 실행 명령은 **hantong**이다. Windows GUI 실행 파일은 `mail-hantong.exe`, CLI는 `hantong.exe`다. 앱 제목, 설치·제거 화면, 도움말, 예제와 문서에 같은 이름을 쓴다. MCP의 `mail.*` 도구 식별자는 기존 계약을 유지한다.

대상은 1단계 Windows 데스크톱 GUI, 승인 도우미, 설정 마법사와 CLI다. 휴대폰 UI는 2단계다. 기존 Windows 승인 도우미에 언어·테마·DPI 표시 패턴이 있으며, 일반 GUI는 별도 권한 없는 표시 계층으로 구현한다. 다음 문서와 사용자가 지정한 참고 저장소를 근거로 한다.

- [v2.3 요건·계획 패키지](README.md): OPS-02·07·08, CLI-01·02·07·16, KEY-05·09, APR-02~04.
- 메일함·계정 경계·승인·접근성 요건은 이 폴더의 Word 통합본과 기능 범위에 포함돼 있다.
- 아래 세 외부 저장소의 README 및 공개 소스. 관찰한 특징과 mail-hantong 적용안을 구분한다.

### 2026-10-30 사용자 화면 피드백 반영

첫 Win32 화면과 이후의 큰 둥근 카드형 시안 모두 최종 시각 디자인으로 채택하지 않는다. 사용자는 Outlook 캡처를 제공하며 프레이밍·전환·스크롤 디자인을 지적했고, Gmail·Superhuman 구성도 허용하며 **현재 시안은 아니라는 뜻을 명확히 했다**. 색상과 모서리만 수정하는 작업을 반복하지 않고 메일 앱의 전체 프레임을 다시 구성한다. 레트로 통신 터미널 테마는 **나중에 추가할 히든 기능**이며 현재 테마 선택기·제품 구현에는 넣지 않는다.

제공된 Outlook 정지 화면에서는 하나로 이어지는 상단 도구 영역, 좁은 폴더 탐색, 밀도 있는 목록과 큰 읽기 영역을 확인했다. 정지 이미지로 실제 전환 효과를 관찰했다고 주장하지 않는다. 초기 웹사이트 참조의 큰 제목·카드는 온보딩에 한정하고 메일 작업 화면에 적용하지 않는다.

- 작은 브랜드와 상태가 있는 얇은 상단 바, 이어지는 도구 영역, 폴더·목록·읽기의 연속된 평면을 만든다. 대형 브랜드·중복 제목·큰 카드 간격을 제거한다.
- 왼쪽 탐색은 약192–208DIP, 행 높이는 약32DIP로 정돈한다. 메일 목록보다 설정·연결 안내가 더 두드러지지 않게 한다.
- 계정/폴더 범위와 읽기 필터는 도구 영역에서 쉽게 확인한다. 기본 Win32의 밝은 테두리·화살표를 어두운 화면에 그대로 남기지 않는다.
- 목록은 간결한 발신자·제목·시각 행으로 구성하며, 읽기 영역이 넓은 창의 주 공간을 차지한다. 얇은 구분선과 표면 차이를 사용하고 좁은 창에서 상세를 아래로 배치한다.
- 스크롤은 콘텐츠에 붙는 얇은 트랙과 둥근 thumb를 사용한다. 기본 약4–6DIP, hover/drag 약8DIP, 충분한 실제 조작 폭을 확보하고 긴 내용에서만 표시한다. 마우스 휠·드래그·페이지 이동·키보드·접근성 범위를 보존한다.
- 선택과 표시 전환은 약120–160ms로 짧게 제공한다. 실제 동작/데이터 적용을 지연하지 않으며 유휴 중에는 프레임을 반복 그리지 않는다. OS 애니메이션 비활성·고대비·모션 감소에서는 즉시 전환한다.
- 사용 가능한 기능만 실제 동작으로 연결하며 가짜 검색창·메일 수·작성 버튼을 채우지 않는다. HWND 기반 키보드·접근성 의미와 기존 승인/조회 동작을 유지한다.

차분하고 명확한 개인 메일 작업 공간을 지향한다. 계정 배지, 발신 주소, 저장·동기화 상태, 승인 대상과 결과가 신뢰를 만든다. 큰 홍보 문구나 장식이 실제 메일·오류·경고보다 강조되지 않게 한다. 이름은 번역하지 않고 `mail-hantong`을 유지한다.

## 제품 목표

여러 계정의 조회·작성·정리와 AI 보조를 같은 작업 공간에서 제공한다. 사용자는 어느 계정에서 무엇을 처리하는지 알 수 있어야 하며, 발송 전에는 대상과 내용을 검토한다. 핵심 흐름은 두 언어와 모든 테마에서 키보드만으로 완료할 수 있어야 한다. 웹사이트의 홍보 전환율이나 3D 연출은 이 앱의 목표가 아니다.

## 사용자와 작업

주 사용자는 개인·업무 메일을 함께 쓰는 한 사람이다. 마우스와 키보드로 GUI를 쓰거나, CLI·AI 에이전트에서 조회·초안 작성을 시작한 뒤 신뢰 화면에서 승인한다. 오프라인, 절전 복귀, 긴 메일과 대량 목록에서도 작업 맥락을 유지한다. 실제 계정·외부 서비스 설정은 설치 후 사용자가 수행하는 흐름으로 제공한다.

## 정보 구조

기본 데스크톱 배치는 계정·메일함 탐색, 메시지 목록, 본문·상세의 세 영역으로 구성한다. 탐색에는 받은편지함, 보낸편지함, 임시보관함, 예약메일함, 즐겨찾기, 스팸함, 휴지통, 광고 보기, 폴더·태그를 둔다. 주소록·규칙·설정은 명시적인 진입점을 제공한다.

검색 범위와 선택 계정은 항상 확인할 수 있게 한다. AI 패널은 필요할 때 열며 발신 계정·수신자·승인 정보를 가리지 않는다. 예약, 전송 대기, 승인 대기, 서버 접수, 결과 불명은 서로 다른 상태로 표시한다.

## 설계 원칙

조작 대상과 결과를 가까이 표시한다. 목록에서 선택한 메일의 계정 배지는 읽기·작성·승인 화면까지 이어진다. 위험한 동작에는 구체적인 대상과 효과를 설명한다. 취소·실패·복구가 가능한 범위는 서버 상태에 맞춰 표시한다. 탐색 메뉴 고정과 메일 별표처럼 의미가 다른 기능은 이름·아이콘·상태를 구분한다.

영·한 문자열과 테마는 첫 화면을 만들 때 함께 구현한다. 화면을 먼저 한 언어·한 테마로 완성한 뒤 번역·테마 작업을 마지막 단계로 미루지 않는다. 이 원칙은 메인 GUI보다 먼저 만드는 승인 도우미에도 적용한다.

## 시각 언어

색은 `surface`, `surface-raised`, `text`, `text-muted`, `border`, `accent`, `focus`, `selected`, `success`, `warning`, `danger`처럼 역할별 토큰으로 사용한다. 계정 색만으로 의미를 전달하지 않고 번호·이름·아이콘을 함께 쓴다. 색상값은 라이트·다크 양쪽의 대비 검증을 거쳐 정한다.

한글과 라틴 문자를 함께 읽기 좋은 시스템 글꼴과 대체 글꼴을 사용한다. 행 높이·버튼 너비는 번역문과 확대 배율을 감당해야 한다. 긴 제목은 목록에서 줄임 표시할 수 있으나, 발신 주소·수신자·발송 경고는 상세 검토에서 전체를 확인할 수 있게 한다. 둥근 모서리와 그림자는 영역 구분에 쓰고 정보 밀도를 해치지 않게 한다.

움직임은 상태 변화를 이해하는 데 필요한 짧은 전환으로 제한한다. 장식 애니메이션은 조작을 막지 않으며 모션 감소 설정에서 제거한다. 3D·자동 재생·캐러셀은 핵심 메일 작업 화면에 사용하지 않는다.

## 컴포넌트

공유 대상으로 계정 배지, 메일 행, 탐색 항목, 검색 입력, 작성 필드, 상태 배지, 오류 안내, 승인 요약, 언어·테마 선택기를 정의한다. 각 컴포넌트는 기본·호버·포커스·선택·비활성·로딩·오류 상태를 두 언어와 테마별로 제공한다. 테마·문자열의 기준은 공통 리소스이며 화면마다 색과 문구를 별도로 하드코딩하지 않는다.

코어는 데이터·상태 코드·권한을 소유하고, GUI는 표시 리소스를 소유한다. 번역 파일이나 디자인 토큰이 권한·발송 정책·승인 결속을 바꾸지 못한다.

## 접근성

웹 표준의 [WCAG 2.2 텍스트 대비](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)와 [비텍스트 대비](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)를 데스크톱 시각 검증의 최소 목표로 사용한다. 일반 텍스트 4.5:1, 큰 텍스트 3:1, 조작 요소·선택·포커스 식별에 필요한 경계 3:1 이상을 확인한다. 이 수치를 만족했다는 사실만으로 전체 접근성 적합성을 선언하지 않는다.

키보드 탐색 순서, 명확한 포커스, 화면 읽기 이름·상태·오류 안내를 제공한다. 접근성 이름도 한국어·영어 리소스로 관리한다. 한글 IME 조합 중 단축키가 발송·삭제를 일으키지 않게 한다. 150%·200% 배율과 모션 감소, Windows 대비 테마를 시험한다.

## 언어 정책

GUI 선택값은 `한국어`와 `English`다. 최초 실행 시 Windows 표시 언어가 한국어이면 한국어, 그 외에는 영어를 선택하고 이후 사용자의 명시적 선택을 저장한다. 런타임 변경은 열린 창·팝업·승인 도우미·앱이 만드는 알림에 반영한다. OS가 직접 소유한 인증 화면·제공자 웹 로그인은 해당 시스템의 언어 정책을 따른다.

문구를 키와 매개변수로 구성하며 문장 조각을 이어 붙이지 않는다. 날짜·숫자·복수형·접근성 이름·도움말·오류·빈 상태·확인 문구를 리소스화한다. 한국어와 영어의 키 집합과 매개변수를 자동 비교하고, 누락 키가 있으면 해당 화면을 완료로 판정하지 않는다. 영어 대체 표시는 손상된 리소스의 복구 수단이다.

언어 전환 중 초안·첨부·선택·검색·계정 범위를 유지한다. 승인 화면은 같은 요청과 원문을 다시 표시하고, 표시가 완성되기 전에는 승인 입력을 받지 않는다. 전환만으로 승인을 발급·연장·소비하지 않는다. 메일 원문, 주소, 사용자 폴더·태그 이름과 저장된 UTC 시각은 UI 번역 대상으로 바꾸지 않는다.

CLI는 최초 구현부터 영어를 제공하고 기본 표시 언어를 영어로 한다. 한국어를 선택할 수 있으며, 표시 언어 우선순위는 `--lang en|ko` → 저장한 `cli.language` → `en`이다. GUI의 `ui.language`와 분리한다. 이 키와 옵션의 구체 스키마는 계약 초안에 포함한다.

```text
hantong --help
hantong --lang en accounts list
hantong --lang ko doctor
hantong accounts list --json
```

도움말·오류·경고·설정·진단·승인 대기 안내·자동완성 설명을 영어로 제공한다. 명령·옵션 이름, JSON/NDJSON 키, 상태·오류 코드, 종료 코드, 도구 식별자는 번역하지 않는다. 계약이 사람용이라고 정의한 메시지만 현지화할 수 있다. `--no-input`에서 언어 선택 프롬프트가 생기지 않으며, 메일 데이터와 UTF-8 입출력은 표시 언어와 독립적이다.

## 테마 정책

설정에는 `라이트 / Light`, `다크 / Dark`, `시스템 설정 사용 / Use system setting`을 제공한다. 저장값은 `light`, `dark`, `system`이며 기본값은 `system`이다. GUI 시작과 전환 시 로컬 사용자 설정을 적용하고 재시작 후에도 유지한다. 1단계에서 장치 간 동기화는 요구하지 않는다.

`system`일 때는 실행 중 OS 앱 테마 변경을 반영한다. 사용자가 `light` 또는 `dark`를 선택하면 일반 OS 테마 변경으로 덮어쓰지 않는다. Windows 대비 테마가 켜지면 시스템 색·대비를 우선하고, 해제 시 저장된 선택으로 돌아간다. 이러한 선택과 즉시 적용 방향은 [Windows 앱 설정 가이드](https://learn.microsoft.com/en-us/windows/apps/design/app-settings/guidelines-for-app-settings)와 [대비 테마 가이드](https://learn.microsoft.com/en-us/windows/apps/design/accessibility/high-contrast-themes)를 참고한다.

테마는 메인 창, 설정, 작성 창, 앱 팝업·알림과 승인 도우미에 일관되게 적용한다. 실행 중 전환해도 초안·포커스·선택·승인 요청을 보존하고 승인 동작을 새로 일으키지 않는다. 메일 본문의 원래 HTML 색을 강제로 반전하지 않으며 안전한 기본 배경, 원문 보기와 읽기 대안을 제공한다. 외부 이미지 차단 등 기존 보안 정책은 그대로 적용한다.

## 창 크기와 반응형 동작

넓은 창에서는 세 영역을 유지하고 사용자가 폭을 조절한다. 좁아지면 보조 패널을 접고 목록↔본문 전환을 제공한다. 계정·발신자·승인 정보와 주요 동작이 화면 밖으로 사라지지 않게 한다. 정확한 최소 폭과 전환점은 ADR-002 프로토타입에서 한글·영어 및 확대 배율로 확정한다. 호버 전용 기능에는 키보드 진입점이 있어야 한다.

## 상호작용 상태

로딩은 진행 범위와 취소 가능 여부를 표시한다. 빈 상태는 이유와 가능한 다음 동작을 설명한다. 오류는 안정적인 코드와 복구 동작을 보여 주되 비밀값·메일 원문을 노출하지 않는다. 성공 표시는 서버 접수와 실제 전달 완료를 구분한다. 비활성 기능은 제공자·권한·정책 중 어느 조건 때문인지 설명한다. 오프라인에서는 마지막 동기화와 로컬 저장 상태를 보이며, 결과 불명 발송을 성공이나 자동 재시도로 표시하지 않는다.

## 문구와 용어

짧고 구체적으로 쓴다. 한국어는 존댓말 안내를 기본으로 하고 영어도 같은 의미·경고 수준을 유지한다. 예약메일함은 Scheduled, 임시보관함은 Drafts, 즐겨찾기는 Starred, 스팸함은 Spam, 광고 보기는 Promotions처럼 용어집을 관리한다. 폴더 고정은 Pin으로 구분한다. 승인·취소·복구 문구는 번역으로 의미가 약해지지 않게 검토한다.

## 구현 제약과 검증

GUI는 [ADR-002](../adr/ADR-002-desktop-ui.md)에 따라 현재 고정된 Windows binding으로 Native Win32를 사용한다. 이 가이드가 React·Tailwind·Spline 등의 도입을 지시하지 않는다. 리소스와 토큰은 선택한 프레임워크의 공통 경로로 관리하고 기존 코어의 정책·승인·감사 경계를 유지한다.

각 GUI 카드의 완료 조건에 한국어·영어 × 라이트·다크·시스템 선택을 포함한다. 시스템 선택은 OS 라이트·다크 양쪽과 실행 중 변경을 시험한다. 승인 도우미·설정·빈 상태·오류 화면까지 화면 검수와 키보드·화면 읽기 검증에 포함한다. 브랜드명, `hantong --help`, 영어 오류·진단, 언어와 무관한 기계 출력도 Gate 1에서 확인한다. 번역 키 존재만으로 문장·레이아웃 검수를 대신하지 않는다.

## 남은 디자인 결정

- 색상값, 글꼴 대체 순서, 행 높이·창 최소 폭: GUI 담당자가 ADR-002 프로토타입에서 양 언어·양 색상·대비 테마로 검증해 기록한다.
- 로고·앱 아이콘: 제품명은 확정됐으며 자산은 아직 없다. 아이콘 제작 시 작은 크기와 두 테마에서 식별성을 검증한다.
- 현지화 용어집의 세부 번역: GUI·CLI 공통 리뷰에서 확정한다. 필수 언어·테마 범위는 이 결정 때문에 뒤로 미루지 않는다.


## 첫 데스크톱 구현의 구체 선택

표시 모델과 양 언어 리소스는 `crates/hantong-desktop`에 둔다. 일반 창은 승인 도우미를 불러오지 않으며 그 모듈의 OS 표시·수명 관리 패턴만 참고한다. 상세 표시 경계는 [desktop-shell](../contracts/desktop-shell.md)이다. 표시 계층은 메일 접근 권한을 만들거나 CLI 프로필을 사용하지 않는다.

기본 창은 1120×740DIP이며 탐색·목록·상세의 세 영역을 사용한다. 창이 좁으면 상세 영역을 목록 아래에 배치한다. 미연결·미관측·캐시 목록 상태를 구분한다. 계정·폴더·메일 행을 명시적으로 선택하며 다른 계정의 늦은 응답으로 선택을 덮어쓰지 않는다. 연결 요청, 등록 상태 확인, 일반 새로고침은 별도 동작이다. 발송·삭제·동기화 행동을 연결된 것처럼 제공하지 않는다.

라이트는 밝은 회색 배경과 흰 surface, 짙은 본문과 파란 강조를 사용한다. 다크는 짙은 남색 배경과 회색 남색 surface, 밝은 본문과 연한 파란 강조를 사용한다. `background/surface/raised/text/muted/border/accent/selected/focus` 토큰을 모델에서 제공한다. 본문·보조·강조 텍스트4.5:1, focus·구분선3:1을 검사하고 고대비는 Windows 사용자 색을 따른다. 둥근 카드나 장식보다 표준 컨트롤의 포커스·키보드·읽기 이름을 먼저 유지한다.

언어와 테마 전환은 실행 중 즉시 적용하며 현재 탐색·연결·메일 선택 상태를 보존한다. 선택은 창 수명 안에서만 유지하며 화면에 이를 표시한다. 재시작 후 표시 설정 저장, 본문·첨부·작성·발송과 나머지 GUI 기능은 후속 구현이며 OPS-07/08 전체 완료로 표시하지 않는다.
